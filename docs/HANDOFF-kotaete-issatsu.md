## 1. 組織とプロジェクトの背景

- 運営会社は**自費出版**を事業とする（幻冬舎メディアコンサルティング ルネッサンス局）。
- **GLO（ゴールドライフオンライン／renaissance-media.jp）** は連載小説のWebメディア。主読者は40〜60代女性。
- 社長から「本を書きたいけれど書けない人に、質問形式で答えてもらうと原稿ができるサイトは作れないか」と相談があった。
- 上司の疑問は「作ってもGLOにどう活かすのか」。これに対する答えが3章の「循環設計」。
- 上司から試作版の作成を依頼済み。**質問項目は上司が決める**という分担。そのため試作版は画面上で設問を編集できる構造にしてある。

## 3. GLOへの活かし方（上司の疑問への回答／設計の背骨）

**一方通行の送客ではなく「循環」として設計する。**

```
① GLOの読者（記事下リンクに入口を置く）
   ↓
② 「こたえて、一冊」に答える（約10分、GLOドメイン内に滞在）
   ↓
③ 構成案ができる（目次＋冒頭原稿を手にした状態）
   ↓
④ 出版の相談へ（「構成案を持った人」として担当者につながる）
   ↓
⑤ 本ができる（著者が1人増える）
   ↓
⑥ その本がGLOの連載になる → 著者とその家族・知人がGLOに来る → ①へ戻る
```

### いま追っているGLOのKPIへの効き方

| 指標 | 効き方 |
|---|---|
| **Direct流入** | 著者とその周囲は検索ではなく直接来る（URL直接入力・ブックマーク） |
| **エンゲージメント率／リピート率** | ツール利用そのものが10分前後の長い滞在 |
| **記事本数** | 集まった原稿から編集が選んで「読者の自分史」コーナーとして連載 |
| **営業の質** | ジャンル・読ませたい相手・いちばんの思い出まで答えたリードは、資料請求より遥かに濃い |

### 測る指標（目標値は検証1カ月で置き直す前提の仮置き）

- 入口のクリック率（記事下リンク → ツール）
- 完了率（質問1に答えた人のうち原稿まで到達した割合。まず50%を目安）
- 離脱した質問番号（どの設問で止まるか → 設問を削る判断に使う）
- 出版相談の申込数（本命のCV）
- 出版契約数
- 副次：GLOのDirect UU、エンゲージメント率、ツール利用者の滞在時間

## 4. アーキテクチャ（本番実装の方針）

### 4.1 重要な技術的制約

**GitHub Pages では JavaScript は動くが、サーバー側でコードを実行できない。**
そのため AI 呼び出しに必要な API キーを隠しておく場所がない。JavaScript に書くと「ページのソースを表示」で誰でも読み取れ、第三者に使われて請求が膨らむ。

→ **AI を呼ぶ処理だけを小さな中継サーバー（Cloudflare Workers / Vercel Functions など、数十行）に肩代わりさせる。** キーはそこに保管する。サイト本体は GitHub Pages のままでよい。

### 4.2 3案とその順番

| 案 | 置きかた | 位置づけ |
|---|---|---|
| **A案（完了）** | Claudeアーティファクト | 社内検討用。**AI機能を使うアーティファクトは組織内にしか共有できない仕様**で、一般読者には開けない。生成は閲覧者自身のClaudeアカウント利用量を使うため費用はかからない |
| **B案（本命）** | GitHub Pages に置き、Media Weaver（社内CMS）の記事ページに iframe で埋め込み＋AI呼び出し用の中継サーバー | GLO内に自然に置ける。GA4でそのまま計測できる。SEO資産もGLOに積み上がる。制作は実質1〜2週間 |
| **C案（将来）** | 独立Webアプリ（独自ドメイン・会員登録・データ保存・営業連携） | B案の数字を見てから判断 |

### 4.3 暴走防止（必須）

1. APIキーは中継サーバーにのみ置く
2. 1人あたりの生成回数に上限を設ける
3. 月額の上限アラートを設定する

## 5. コスト（2026年9月時点のClaude API公開価格・1ドル150円換算の概算）

| 単位 | 金額 |
|---|---|
| 置き場所（GitHub Pages＋Workers無料枠） | 0円 |
| **入口1回**（タイトル案・目次・冒頭原稿を1回生成／約3,000トークン） | **3〜8円** |
| **書籍1冊 完走**（10万字＝四六判200ページ相当／12章／書き直し1.8回込み） | **200〜900円**（重い使い方でも2,200円が上限目安） |
| 検証1カ月（入口100名・完走数名） | 1,000円程度 |
| 本格運用（月10冊完走） | 4,000円程度 |

参考価格：Sonnet 5 = 入力$2／出力$10、Haiku 4.5 = 入力$1／出力$5、Opus 5 = 入力$5／出力$25（いずれも100万トークンあたり）。
プロンプトキャッシュはヒット時に入力価格の10%、Batch API は入出力とも50%引き。

### コスト設計上の重要な方針

**費用の大半は「出力した文字数」で決まる。** よって：

- **書籍1冊をその場で一気に生成させない。** 待ち時間が数十分になり、離脱者のぶんまで費用が出て、何より「全部AIが書いた本」になってしまう。
- **章ごとに「質問する → その章を書く → 本人が直す」を繰り返す形にする。** 費用が完走者に分散し、自費出版として筋も通る。
- 構成案や要約は Haiku、本文のみ Sonnet、生成は夜間バッチ（「明朝メールでお届けします」で成立する）にすると1冊200円前後に収まる。

## 6. 試作版の実装仕様（添付 `kotaete-issatsu-prototype.html`）

素のHTML/CSS/JS、ビルド不要の1ファイル。フレームワーク・ライブラリなし。

### 6.1 画面構成

2タブ構成。

- **「設問をつくる」** — 設問エディタ（上司が使う）
  - 質問文・ヒントの書き換え
  - 答え方の切り替え（`choice` 選択式／`line` 1行記入／`para` 文章記入）
  - 選択肢の追加・削除・編集
  - 質問の追加・複製・削除・↑↓で並べ替え
  - 必須／任意の切り替え
  - 「できあがる原稿の設定」：章数・冒頭字数・AIへの申し送り
  - 保存 / 設定を書き出す(JSON) / はじめの設問に戻す
- **「試してみる」** — 読者が見る画面そのまま
  - 1問1画面、プログレスバー、もどる／次へ
  - 最後に生成 → タイトル案・目次・冒頭原稿を表示
  - 原稿をテキスト保存 / もう一度つくる / やり直す

### 6.2 データ構造

```jsonc
{
  "questions": [
    {
      "id": "q1",
      "text": "どんな本を書きたいですか。",
      "hint": "いちばん近いものを、ひとつ選んでください。",
      "type": "choice",          // "choice" | "line" | "para"
      "required": true,
      "choices": ["自分史・回想録", "エッセイ・日々の暮らし", "..."],
      "example": ""              // line/para のときのプレースホルダ
    }
  ],
  "output": {
    "chapters": 6,               // 目次の章数
    "openingChars": 1000,        // 冒頭原稿の字数
    "extra": "・ご本人が語る一人称で、聞き取った場面から書き起こす。\n・数値（年齢・時刻・金額・人数など）は漢数字ではなく算用数字で書く。例：「十九時」ではなく「19時」。\n・聞き取っていない事実を作り込みすぎない。細部はご本人が書き足せるよう、控えめにしておく。\n・読者は40〜60代。むずかしい言葉を避け、声に出して読める日本語で書く。"
  },
  "updatedAt": "ISO8601"
}
```

**初期設問は8問**（自分史向けに設計済み。自由記述は2問だけに絞ってある — 書けない人のためのサイトが入力欄だらけでは本末転倒なため）:

1. どんな本を書きたいですか。（選択）
2. その本を、誰に読んでほしいですか。（選択）
3. 本の中心に置きたいのは、どの時期のことですか。（1行）
4. その中で、いちばん心に残っている場面を教えてください。（文章）← **本文の核**
5. そのとき、どう感じましたか。（文章・任意）
6. 読んだ人に、何を持ち帰ってほしいですか。（選択）
7. どんな語り口がお好きですか。（選択）← 文体の指定に使われる
8. お名前、またはペンネームは。（1行・任意）

### 6.3 生成プロンプトの組み立て（`buildPrompt()`）

```
あなたは自費出版社の熟練した編集者です。本を書きたいけれど書き出せずにいる方から、次のように聞き取りました。

■ {質問文}
　{回答 または （お答えなし）}
…（全設問ぶん繰り返し）

この方の本の「タイトル案」「目次」「冒頭原稿」を作ってください。

【守ること】
・見出しは【タイトル案】【目次】【冒頭】の3つだけを、この順で使う。前置きも後書きも書かない。
・【タイトル案】は3案。1行ずつ「1. タイトル ｜ ひとことの説明」の形で書く。
・【目次】は{chapters}章。1行ずつ「第1章　章タイトル ｜ その章に書くこと（40字程度）」の形で書く。
・【冒頭】は第1章の書き出しを{openingChars}字程度。
・文体は「{語り口の回答}」。      ← 質問文が /語り口|文体|調子/ にマッチする設問の回答を自動で拾う
{output.extra をそのまま追記}
```

### 6.4 出力のパース（`parseDraft()`）

`/【\s*(タイトル案|目次|冒頭)\s*】/g` で3セクションに分割。

- **タイトル案** — 行頭の `1. ` 等を除去し、`｜` または `|` で「タイトル」と「説明」に分割
- **目次** — 同じく `｜` で「第N章 章タイトル」と「書くこと」に分割
- **冒頭** — そのまま本文として表示（`white-space: pre-wrap`、明朝で組む）

ストリーミング中も毎回パースして描画するので、書かれている途中から画面に出る。

### 6.5 アーティファクト固有の実装（本番では置き換える）

試作版は Claude アーティファクトの runtime capability を使っている。**B案に移すときはここを差し替える。**

| 試作版 | 本番での置き換え先 |
|---|---|
| `claude.use("sample")` でAI生成 | 中継サーバー経由の Claude API 呼び出し（ストリーミング対応） |
| `claude.use("db")` で設問を組織内共有保存 | 設問JSONを静的ファイルとしてリポジトリに置く、またはCMS/KVに保存 |
| `claude.use("downloads")` でテキスト保存 | 通常の Blob ダウンロード |

すべて `null` 返却時のフォールバック処理を実装済みなので、差し替えの当たりはつけやすい。

### 6.6 デザイン仕様

**方向性**：`lp.yoom.fun` 参照の、大胆な色ブロック・太い丸ゴシック・大きな角丸。ただしオリジナル。
**禁止**：Claudeが作りがちな既視感のあるデザイン（クリーム地＋セリフ＋テラコッタ、紫→青グラデーション、Inter/Space Grotesk、絵文字の見出しマーカー、全部同じ角丸カード）。

```css
/* ライト */
--ground:#F1EFEA;  --card:#FFFFFF;  --card-2:#F8F7F4;
--ink:#17233A;     --ink-soft:#5A6478;  --ink-faint:#8C95A6;
--line:#E4E1DA;    --line-2:#EFEDE7;
--coral:#E8503A;   --t-coral:#FBE7E3;   /* 主アクション */
--amber:#E5A900;   --t-amber:#FBF0D3;
--teal:#219E83;    --t-teal:#DCF1EA;    /* 選択中の状態 */
--violet:#6353C9;  --t-violet:#E7E3FA;  /* フォーカス */
--block:#17233A;   --on-block:#F6F7FA;  --on-block-soft:#AFB8CC;
--r-xl:34px; --r-lg:22px; --r-md:14px; --pill:999px;
```

ダークテーマも実装済み（`prefers-color-scheme` と `[data-theme]` の両方に対応）。

**書体**（Google Fonts）
- 見出し・UI：`Zen Maru Gothic`（500/700/900）
- 本文・入力：`Zen Kaku Gothic New`（400/500/700）
- **生成された原稿の本文のみ `Shippori Mincho`** — UIは軽やか、原稿は本らしく、という対比が効いている

**設問カードの色** — 4色（violet → teal → amber → coral）を順に循環させ、左の色帯とQ番号チップに適用。

### 6.7 ヒーローのアニメーション（11秒ループ・インラインSVG＋CSS keyframes）

「原稿が本になるまで」を描いた作り込みの演出。**幼く見せないことが要件**だったので、以下の点が肝：

1. **万年筆が現れる**（ペン先・スリット・クリップ・金の胴輪まで描く。クレヨン状の鉛筆はNG）
2. **原稿用紙が立ち上がる**（8×8のマス目、朱の罫、社名入り。大学ノートの横罫はNG）
3. **縦書きで文字を1画ずつ書く**（右の列から左へ。ペンは列を上から下へなぞり、行末で左隣の列の頭へ跳ぶ。波線のなぐり書きはNG）
   - 実装：列ごとに1本の `<path>`、`pathLength="100"` ＋ `stroke-dashoffset` を100→0でアニメーション
4. **右綴じで右へ倒れるページめくり**（`transform-origin: right center` ＋ `scaleX(1→0)`、グラデーションで巻きの陰影）
5. **本ができあがる**（小口＝ページの束・背・帯・箔押しの罫。表紙には「こたえて、一冊」が縦組みで入る）
6. **表紙を光がゆっくり横切る**（`clipPath` ＋ skew したグラデーション矩形の平行移動。星のキラキラはNG）

`prefers-reduced-motion` では、できあがった本だけを静止画として表示。

### 6.8 高齢者向けの配慮

- 本文16.5px、選択肢17px、ヒント15.5px（小さくしない）
- 選択肢は大きなカード＋丸いラジオ印（タップ領域を広く）
- 自由記述は最小限、選択式を中心に
- 英語ラベルは極力避ける（読者が見る画面では「質問」など日本語）

8. 出版相談フォームと営業フローの接続

- どの章で何を聞くか（章別の設問設計）

- 個人情報の扱い（**検証段階では生成物を保存しない**方針。保存すると一気に重くなる）

## 8. よく出る質問と回答（社内説明用）

| 質問 | 回答 |
|---|---|
| AIが書いた原稿を自社で出版していいのか | ツールが作るのは**叩き台まで**。仕上げは人。初回打ち合わせで「何を書きたいのか」を聞き出す時間を短縮する道具として位置づける |
| 変なものが生成されて炎上しないか | 生成結果は**入力した本人にしか表示しない**。保存もしない。GLOに載せるのは編集が選別したものだけ |
| すでに書ける人には要らないのでは | そのとおり。ねらいは**「書きたいけれど1行目が書けない人」**。この層はこれまで資料請求フォームまで来ないまま消えていた |
| 個人的な内容を持っておかなくていいのか | 検証段階では持たないのが正解。まず完了率と相談への転換率だけを測る |
